# Labo Manager (Labbora) — LIMS du LRARVY / ONSSA

Application web de gestion de laboratoire qui remplace la base Access « BD Réception des échantillons » du Laboratoire Régional d'Analyses et de Recherches Vétérinaires (LRAR Tanger, ONSSA, Maroc). Déployée sur le réseau local du labo. Interface et messages **en français**.

Trois sections :
- **SMA** — Microbiologie Alimentaire
- **SCHA** — Sécurité Chimie Hygiène Alimentaire
- **SSA** — Santé Animale

## Stack

- **Backend** : Python, FastAPI, SQLAlchemy async (asyncpg), Pydantic v2, sessions par cookie signé (`SessionMiddleware`), bcrypt. PDF via **ReportLab** (WeasyPrint écarté : problèmes GTK sous Windows). Excel via **openpyxl**.
- **Base** : PostgreSQL, base `labo`.
- **Frontend** : React 18 + Vite + react-router-dom v6 + **Ant Design 6** (`antd`, `@ant-design/icons`, `dayjs` en locale `fr`). Thème dans `main.jsx` (`ConfigProvider`) ; `frontend/src/style.css` ne contient plus que des compléments.
- **OS de dev** : Windows.

## Lancer le projet

```bash
# Backend (depuis backend/, venv .venv activé)
pip install -r requirements.txt          # requirements-dev.txt en plus pour les tests
python scripts/migrer.py                 # migrations en attente
uvicorn app.main:app --reload --port 8000

# Tests du backend (base labo_test reconstruite à chaque lancement, jamais labo)
powershell -ExecutionPolicy Bypass -File scripts\tester.ps1           # tout + couverture
powershell -ExecutionPolicy Bypass -File scripts\tester.ps1 -Filtre droits

# Frontend (depuis frontend/)
npm install
npm run dev        # http://localhost:5173, proxy /api -> http://localhost:8000
npm run build      # dist/ servi par FastAPI en production
npm run e2e        # build puis tests Playwright (serveur de test sur labo_test, port 8020)
```

Configuration : `backend/.env` (modèle commenté `backend/.env.exemple`) : URL de la base, clé secrète, environnement (`production` / `test` / `developpement`), durées de session, dossiers des journaux et des sauvegardes. Le fichier `.env` contient des secrets : il n'est jamais diffusé.

## Déploiement cloud (démo)

Démonstration publique, **données fictives seulement** ; la production du labo reste sur le serveur local.
- Front : GitHub Pages (`https://<utilisateur>.github.io/<depot>/`), publié par `.github/workflows/pages.yml` à chaque push sur `main` touchant `frontend/**` (build avec `VITE_BASE=/<depot>/`, `VITE_API_URL` = variable de dépôt, `VITE_ENVIRONNEMENT=demo`, copie `index.html` → `404.html` pour les routes profondes).
- API : Render (`render.yaml`, `rootDir: backend`, santé `/api/health`). Variables : `ENVIRONNEMENT=demo`, `DATABASE_URL` (chaîne Neon **directe**, collée telle quelle), `SECRET_KEY` (générée par Render), `CORS_ORIGINS=https://<utilisateur>.github.io` (sans chemin), `SESSION_HTTPS=1`.
- Base : Neon, remplie depuis un poste par `python scripts/init_demo.py` (depuis `backend/`, `DATABASE_URL`, `DEMO_ADMIN_MDP` et `DEMO_MDP` en variables d'environnement ; relançable ; refuse la base `labo`).
- Mise à jour : push sur `main` (Render redéploie l'API, le workflow republie le front) ; nouvelle migration : relancer `init_demo.py` (il applique les migrations en attente).

Après un changement backend : relancer uvicorn (et vider `__pycache__` si comportement étrange). Après un changement front en prod : `npm run build` puis Ctrl+F5.

## Règles métier en place (ne pas casser)

- **Rôles** (`app/core/security.py`, repris dans `components/ui.jsx`) : `admin`, `responsable`, `user` voient toutes les sections (`ROLES_GLOBAUX`) ; `sma`, `scha`, `ssa` ne voient que leur section. Le contrôle d'accès est **toujours vérifié côté serveur**.
  - **Valider, renvoyer, émettre un rapport, lancer un erratum** : `responsable` et `admin` seulement (`ROLES_RESPONSABLES`). `user` garde la lecture globale et la réception, mais ne valide pas et n'émet pas (il peut télécharger un rapport déjà émis).
  - **Stepper manuel de statut** (`PATCH /api/echantillons/{num}/statut`) : `admin` seulement (403 sinon) ; ne mène jamais à `Validé` ni à `Rapport émis` (409), et ne fait pas sortir un dossier de `Rapport émis` (409 : passer par l'erratum).
  - Notifications « À valider » : `admin` et `responsable` ; `user` ne reçoit que les retards.
- **Une seule section par échantillon** : le formulaire utilise des boutons radio, et `_valider_section_unique()` refuse 0 ou plusieurs sections (création et modification).
- **Numérotation automatique** : format `AAAA-SECTION-NNNN` (ex. `2026-SSA-0001`), compteur propre à chaque section, remis à zéro chaque année, calculé par max+1 avec retry anti-collision (`_next_num` dans `echantillons.py`). Ne pas changer ce format sans demande explicite.
- **Décision de réception** (migration 017, tâche 14) : `Accepté` (par défaut à la création) / `Accepté sous réserve` / `Refusé`, motif obligatoire pour les deux dernières (400) ; température à réception et cases de non-conformité (`nc_temperature`, `nc_contenant`, `nc_quantite`, `nc_etiquetage`, `nc_delai`, `nc_autre`) ; le texte `non_conformite` reste l'observation. NULL (échantillons antérieurs) = accepté. Un échantillon **`Refusé` ne peut pas recevoir de fiche de traitement** (409 sur la fiche, la soumission et les résultats : `refuser_si_refuse`), n'est jamais compté « en retard », et s'affiche avec un `Tag` « Refusé » (pas de nouveau statut). Le bloc II du rapport reprend la température, l'état (« Non conforme : … ») et la réserve.
- **Facturation et paiement** (bloc P, tâches 34 à 41, `services/facturation.py`, `bulletins.py`, `paiements.py`, `routers/facturation.py`, guide `docs/facturation.md`) :
  - Montants en `numeric(12,2)`, arrondis au centime (demi supérieur), affichés `1 250,00 DH`. TVA : taux réglable (`parametres`, 0 % par défaut ; à 0, pas de ligne TVA sur les documents), figé sur le bulletin à son émission.
  - **Grille tarifaire datée** : `ref_tarifs` (une analyse = un tarif par section, nom comparé sans casse ni espaces de bord, `par_prelevement`, `a_valider`, `actif`) + historique `ref_tarifs_prix` (périodes). Modifier un prix ouvre une nouvelle période à la date d'effet (jamais future) sans écraser l'ancienne ; un tarif avec historique ne se supprime pas (409, le désactiver). Analyse du catalogue sans prix en vigueur = « prix à renseigner ».
  - **Lignes facturables** (`factures_lignes`) : proposées automatiquement à partir des analyses saisies (à l'enregistrement des résultats), ou ajoutées à la main (analyse de la grille, frais divers). **Le prix est figé à la création de la ligne** : un changement de tarif ne modifie jamais une ligne ni un bulletin existant. « Par prélèvement » : quantité = prélèvements de la section.
  - **Bulletin** (`factures`) : brouillon (échantillons d'un **même client**), puis émission = numéro `BUL-AAAA-NNNNN` (séquence annuelle, verrou consultatif, sans trou ni doublon ; format dans `FORMATS_NUMERO`), copie figée des lignes (`factures_details`), PDF archivé + SHA-256, lignes verrouillées. **Un bulletin émis n'est plus modifiable** (409) : correction par un **avoir** (`AV-AAAA-NNNNN`, lignes ou montant, motif obligatoire, responsables), puis nouveau bulletin si besoin. Émission refusée s'il reste un prix à renseigner.
  - **Encaissements** (`paiements`) : partiels acceptés ; au-delà du reste dû, confirmation explicite (trop-perçu signalé) ; quittance `Q-AAAA-NNNNN` ou n° du carnet de la régie, reçu PDF archivé. **Jamais de suppression d'encaissement** : annulation avec motif (responsables), exclue des totaux.
  - **Exonération** (`exonerations`) d'un bulletin émis ou d'un échantillon non facturé : type (contrôle officiel, convention, autre) et motif obligatoires, responsables ; annulable avec motif.
  - Statut de paiement : `Non payé`, `Partiellement payé`, `Payé`, `Exonéré`, `Avoir total` (`Non concerné` sans facturation), calculé et recopié dans les champs historiques de l'échantillon (`Payement`, `TOTAL`, `Montant payé`, dernier mode / date / quittance) ; un bulletin regroupé est réparti au prorata entre ses échantillons. Ces champs ne se saisissent plus (recalculés à chaque modification de l'échantillon).
  - **Étape exigée** (réglage `etape_paiement`) : `aucune` (défaut : avertissement seulement), `mise_en_analyse` (création de la fiche de traitement refusée, 409) ou `remise_rapport` (1re émission du rapport refusée, 409) tant que l'échantillon n'est ni payé, ni exonéré, ni soldé par avoir.
  - Droits : tarifs et réglages = admin ; lignes, bulletins, encaissements = accueil (`user`) et admin ; avoirs, exonérations, annulations d'encaissement = responsables (`responsable`, `admin`) ; lecture des montants = rôles globaux ; **rôles de section : statut de paiement seulement** (403 sur les montants et le jeu de reporting `facturation`).
  - Notifications : bulletins impayés depuis plus de N jours (`seuil_impayes_jours`, 30) pour l'accueil et l'admin.
- **Équipements** (tâche 17, `services/equipements.py`) : la fiche de traitement désigne l'équipement par son **code** (`equipement_utilise`) ; à l'enregistrement, un code nouveau doit exister, être actif et appartenir à la section (ou être commun), sinon 400. Une fiche est **contestable** si son équipement est hors étalonnage (aucun étalonnage conforme couvrant la date) ou en panne à la date de l'analyse (mise en analyse, sinon 1re date d'analyse, sinon aujourd'hui) : alerte sur la fiche et notification aux responsables. Échéances (étalonnage / vérification = dernière date + périodicité) : alerte 30 jours avant, dans les notifications (sauf `user`). Création / modification : responsables ; événements : responsables et analystes de la section ; suppression : admin, et seulement sans historique ni utilisation (sinon désactiver).
- **Habilitations** (tâche 19, `services/habilitations.py`, `routers/habilitations.py`) : matrice utilisateur × analyse × section (qualification, échéance facultative). À l'enregistrement des résultats, toute ligne nouvelle ou modifiée exige une habilitation à jour du saisisseur pour son analyse (nom comparé sans casse ni espaces de bord), sinon 403 ; les lignes inchangées ne sont pas re-contrôlées. `HABILITATIONS_OBLIGATOIRES=0` suspend le contrôle (saisie initiale de la matrice). Écriture : responsables ; lecture : tout pour les responsables, ses propres habilitations pour les autres. Alerte 30 jours avant l'échéance (notifications).
- **Contrôles qualité internes** (tâche 18, `services/controles_qualite.py`) : séries par section et méthode (témoin positif / négatif, blanc, duplicata, matériau de référence). Quantitatif : moyenne et σ de référence (sinon calculés sur les mesures, n − 1), limites ±2σ / ±3σ ; **alerte** si une valeur est hors ±3σ, ou au 7e point consécutif strictement du même côté de la moyenne (et suivants). Qualitatif : alerte si résultat ≠ résultat attendu. Une série est « en alerte » quand sa dernière mesure l'est (notifications, sauf `user`). Séries : responsables ; mesures : responsables et analystes de la section.
- **Réactifs et milieux de culture** (tâche 20, `services/reactifs.py`, `routers/reactifs.py`) : un lot = code interne `L<AAAA>-<NNNN>` (attribué à la création), produit, catégorie, n° de lot fournisseur (couple produit + n° unique), section ou commun, péremption, stock et seuil d'alerte. Le stock ne change que par les mouvements (sortie, entrée, inventaire) ; une sortie ne peut pas dépasser le stock (400). La fiche de traitement cite ses lots par leur code dans `lot_reactif` (séparés par des virgules) : un lot nouvellement choisi doit exister, être actif, de la section (ou commun) et **non périmé à la date de l'analyse** (mise en analyse, sinon 1re date d'analyse, sinon aujourd'hui), sinon 400 ; les lots déjà présents ne sont pas re-contrôlés. Traçabilité dans le détail de l'échantillon et, en sens inverse, sur chaque lot. Alertes (sauf `user`) : périmé, péremption dans les 30 jours, stock sous le seuil. Lots et mouvements : responsables, et analystes pour leur section ; suppression : admin, seulement sans mouvement ni utilisation.
- **Reporting** (tâches 21 à 25, `services/requetes.py`, `routers/requetes.py`, `routers/bilans.py`) :
  - **Pas de SQL libre.** Jeux de données, critères (regroupements et filtres), mesures et dates de référence sont choisis dans le **catalogue fermé** de `services/requetes.py` ; chaque entrée est une expression SQL écrite dans le code, toute valeur saisie est un paramètre. Une clé hors catalogue → 400. Seul l'admin reçoit le SQL exécuté (contrôle).
  - Droits : un rôle de section ne voit que sa section (requêtes, détail, valeurs des filtres, exports, requêtes partagées, bilans) ; filtre sur une autre section → 403. Le jeu `facturation` lui est refusé (403).
  - Jeu `facturation` (tâche 40) : journal des mouvements des bulletins émis (`MOUVEMENTS` : lignes facturées + TVA, avoirs, exonérations, encaissements) ; reste à recouvrer = facturé − avoirs − exonérations − encaissé ; date de référence = émission du bulletin ou date du mouvement.
  - Libellés des référentiels (code sans libellé : « Type inconnu (code n) ») ; valeurs vides regroupées sous « Non renseigné » ; échantillon à plusieurs sections (données Access) : « Plusieurs sections ». Sous-totaux et total général calculés par la base (`GROUPING SETS`) : la somme des lignes d'un critère égale toujours le total.
  - Conformité d'un échantillon : « Non conforme » si une source l'est (fiche SMA / SCHA, conclusion d'une ligne SCHA, positivité ou comptages SSA), sinon « Conforme » si une source l'est, sinon « Non renseigné » ; taux = NC / (C + NC). Délai = réception → 1re émission officielle (sinon « Date 1 Remise Rapport »).
  - Requêtes enregistrées : personnelles (auteur seul) ou partagées ; modification / suppression par l'auteur ou l'admin ; période relative recalculée à chaque ouverture ; une requête du modèle de bilan ne peut pas être supprimée (409).
  - Bilan mensuel : blocs = requêtes partagées du modèle (`bilan_modele`, admin), période remplacée par le mois du bilan ; chaque génération archivée (`bilans_mensuels`, nouvelle version, SHA-256), jamais écrasée.
- **Statuts** (avec accents, contrainte CHECK en base) : `Reçu` → `En cours` → `À valider` → `Validé` → `Rapport émis`.
- **Validation à deux niveaux** (`traitements.py`) : la 1re saisie passe en `En cours` ; l'analyste **soumet** (`/soumettre`) → `À valider` (fiche verrouillée) ; un responsable (`responsable` ou `admin`) **valide** (`/valider`, double regard obligatoire pour tous, admin compris : valideur ≠ saisisseur) → `Validé`, ou **renvoie** (`/refuser`, motif optionnel) → `En cours`.
- **Sécurité des comptes** (`core/securite_http.py`, `routers/auth.py`, `docs/https.md`) :
  - Session : durée maximale 8 h (`SESSION_MAX_AGE`) **et** expiration après `SESSION_INACTIVITE_MIN` minutes sans activité (30 par défaut) → 401 « Session expirée… », le front revient à la connexion. Les appels automatiques (`/api/notifications`) ne prolongent pas la session.
  - Verrouillage : 5 échecs de connexion consécutifs → compte verrouillé 15 min (`users.echecs_connexion`, `users.verrouille_jusqu`, migration 016), 403 même avec le bon mot de passe ; un succès remet le compteur à zéro ; traces `ECHEC_CONNEXION` / `VERROUILLAGE` dans `AuditLog` (+ `audit_donnees`, utilisateur `connexion:<nom>`). L'admin peut déverrouiller (`POST /api/admin/users/{id}/deverrouiller`).
  - Mot de passe : au moins 10 caractères, avec lettres et chiffres (`security.mot_de_passe_conforme`, même règle côté front `REGLES_MOT_DE_PASSE`), contrôlé à la création, au changement (`POST /api/auth/mot-de-passe`, mot de passe actuel exigé) et à la réinitialisation par l'admin (`POST /api/admin/users/{id}/mot-de-passe`, déverrouille aussi). Les mots de passe existants plus faibles restent valables jusqu'à leur changement.
  - CSRF : sur POST / PUT / PATCH / DELETE `/api/*`, une `Origin` (ou un `Referer`) étrangère est refusée (403) ; acceptés : l'hôte lui-même et `ORIGINES_AUTORISEES` (serveur Vite de dev) ; sans Origin ni Referer (curl, scripts) la requête passe. En plus du cookie `SameSite=Lax` (`Secure` si `SESSION_HTTPS=1`).
- **Rapport d'essai** : refusé (409) tant que le statut n'est pas `Validé` ou `Rapport émis` ; la 1re émission passe le statut à `Rapport émis`.
  - **Rapport figé** (`rapports_emis`) : la 1re émission attribue un numéro officiel `NNNN/CODE/AAAA` (CODE `MA` / `CH` / `SA`, séquence par section remise à zéro chaque année, jamais réutilisée) et stocke le PDF (`bytea`) avec son SHA-256. Ensuite `GET /api/rapports/{section}/{num}` renvoie **le PDF stocké** ; il n'est jamais régénéré.
  - **Erratum** : un responsable rouvre le dossier (`POST /api/rapports/{section}/{num}/erratum`, motif obligatoire) → statut `En cours`, fiche dévalidée ; après correction, soumission et validation, la nouvelle émission crée la version suivante (nouveau numéro, mention « Annule et remplace le rapport n° X du JJ/MM/AAAA » + motif) ; l'ancienne passe à `annulé` et reste téléchargeable (`GET /api/rapports/fichier/{id}`).
- **Résultats (bloc IV)**, colonnes conformes à Access :
  - SMA : RP1 à RP5
  - SCHA : RP1 à RP9 + Moyenne + Conclusion
  - SSA : résultat d'analyse + critères d'interprétation + nombre de positifs / négatifs / douteux
- **Référentiels** : sous-type rattaché à un type (`ref_soustypes_echantillon.type_id`, FK `ON DELETE RESTRICT`). Dans la réception, le choix du type filtre la liste des sous-types (cascade).
- **Traçabilité** : chaque écriture ajoute une ligne `AuditLog` (journal applicatif, conservé).
  - **Journal d'audit inviolable** (`audit_donnees`, migration 015) : des triggers PostgreSQL enregistrent toute écriture (INSERT / UPDATE / DELETE) sur `echantillons`, `traitement_*`, `resultats_analyses`, `rapports_emis`, `users` et `ref_*`, même faite hors application : table, opération, clé, n° d'échantillon, avant / après en `jsonb` (jamais le hash du mot de passe ni le PDF), utilisateur, horodatage. `audit_donnees` refuse UPDATE, DELETE et TRUNCATE. L'utilisateur applicatif est transmis par `get_db` (`set_config('lims.utilisateur', …, true)` à chaque début de transaction) ; à défaut : `pg:<utilisateur PostgreSQL>` (source `base`). Écran admin : `/admin/audit`.

## Conventions techniques et pièges connus

- **Colonnes héritées d'Access** avec espaces, accents et `°` (`"N° Echantillon"`, `"Date reception"`...). Le modèle ORM les mappe vers des attributs propres (`num_echantillon`, `date_reception`...). Pour les tables dont le modèle ne couvre pas toutes les colonnes (résultats, référentiels), on utilise du **SQL brut paramétré** via `sqlalchemy.text()` : c'est voulu, garder ce style.
- **Requêtes toujours paramétrées**, jamais de concaténation de valeurs utilisateur.
- **Nouvelle table métier** : dans sa migration, ajouter `SELECT audit_attacher('ma_table');` (trigger d'audit, clé primaire obligatoire). Les sessions doivent passer par `get_db` (ou `transmettre_utilisateur`) pour que l'utilisateur soit tracé.
- **Migrations** : SQL **additif** uniquement (`ADD COLUMN IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS`), numéroté à la suite (prochaine : `032_...sql`). Exécution : `python scripts/migrer.py` depuis `backend/` (applique, dans l'ordre et chacun dans sa transaction, les fichiers non encore enregistrés dans `schema_migrations` ; `--base labo_test` pour la base de test, `--dry-run` pour voir sans écrire, `--etat` pour l'état ; connexion de `settings.DATABASE_URL`, pas de mot de passe en ligne de commande). **Une migration appliquée ne se modifie plus** : son empreinte SHA-256 est enregistrée et le script s'arrête (code 2) si le fichier a changé ; corriger par une nouvelle migration. Une base sans `schema_migrations` mais avec des tables est refusée : enregistrer d'abord ce qui y est passé avec `--marquer`. Ne jamais casser les données existantes.
- **Tests** (`backend/tests/`, tâche 27) : `pytest` + `httpx.AsyncClient` sur l'application (ASGI, sans serveur). `conftest.py` reconstruit `labo_test` de zéro par `migrer.py` à chaque session (refuse `labo`), crée les comptes `admin_t`, `resp1`, `resp2`, `util1`, `sma1`, `scha1`, `ssa1` (mot de passe `Testlims2026`) et leurs habilitations ; fixtures `clients[nom]` (client connecté, `clients[None]` sans session) et `db` (asyncpg). `dossier(clients, section, etape)` amène un échantillon à `recu` / `saisi` / `soumis` / `valide` / `emis`. Une seule boucle asyncio pour la session (pool de l'application). Couverture : `.coveragerc` avec `concurrency = greenlet` (sinon les lignes après un accès SQLAlchemy async ne sont pas comptées). Toute nouvelle règle métier ou route sensible reçoit son test (et sa ligne dans la matrice `test_droits.py`).
- **Tests de bout en bout** (`frontend/e2e/`, tâche 28) : Playwright 1.56 (la 1.49 se bloque au chargement de la configuration avec Node 24), navigateur Edge installé (`PW_CHANNEL=chromium` pour l'autre). `npm run e2e` construit le front puis lance `serveur_test.py` (base `labo_test` reconstruite, port 8020). Les fichiers s'exécutent dans l'ordre alphabétique, sur une seule base : un test ne doit pas dépendre d'un autre fichier. Repérer les champs par leur libellé (`getByLabel`) et les boutons par leur texte ; pour un Select / AutoComplete antd, `choisir()` de `outils.js` (le placeholder antd 6 n'est pas un attribut de l'input). Les captures (`capture(page, 'NN_nom')`) alimentent le guide utilisateur.
- **Configuration** (`app/core/config.py`, tâche 29) : `pydantic-settings` lit les variables d'environnement puis `backend/.env`. Aucun secret dans le code. Nouveau réglage : un champ dans `Settings` + une ligne commentée dans `.env.exemple`. En `production`, l'application refuse de démarrer si `SECRET_KEY` est la valeur par défaut ou fait moins de 32 caractères.
- **Erreurs et journaux** (`app/core/journal.py`, tâche 29) : toute erreur renvoie `{"detail": "…"}` en français ; une donnée invalide → 422 « Données invalides — champ : message » (+ `erreurs`) ; une exception non prévue → 500 « Erreur interne du serveur (référence XXXXXXXX)… », trace complète dans `logs/lims.log` avec la même référence. Ne jamais renvoyer de trace ni de message d'exception brut au client ; lever `HTTPException` avec un message en français pour les erreurs métier. Chaque requête `/api` est journalisée (méthode, chemin, statut, durée, utilisateur). `JournalMiddleware` est ajouté en dernier (le plus extérieur). La route `/api/test/erreur` n'existe qu'en environnement `test`.
- **Listes volumineuses** (tâche 30) : jamais de liste complète chargée dans le navigateur. `GET /api/echantillons?page=&taille=&tri=&ordre=` renvoie `{lignes, total, page, taille, compteurs}` (compteurs par statut calculés avec tous les filtres sauf le statut ; tri limité aux clés de `TRIS`) ; sans `page`, l'ancienne liste complète reste disponible pour compatibilité (scripts, tests), le front ne l'utilise plus. Tableaux antd en mode serveur : `pagination={{ current, pageSize, total }}` + `onChange` qui recharge (tri `sorter: true`, `sortOrder` contrôlé), retour en page 1 à chaque changement de filtre. Sélection d'un échantillon : `SelectEchantillon` cherche côté serveur (50 résultats). Détail d'une requête : `POST /api/requetes/detail` avec `page` / `taille` (+ `total`). Journal d'audit : `limite` / `decalage`. Recherche partielle (`ILIKE '%…%'`) : servie par les index trigrammes de la migration 026. Vérifier toute nouvelle requête lourde avec `EXPLAIN ANALYZE` sur une base remplie par `remplir_volume.py`, puis `mesurer_performances.py`.
- **Démonstration en ligne** (front et API sur deux sites) :
  - API : `BASE = (VITE_API_URL ?? "") + "/api"` dans `client.js` (vide en local : proxy Vite ou même origine).
  - Jeton : `POST /api/auth/login` renvoie aussi `jeton` (itsdangerous, durée `JETON_DUREE_MIN`, sinon `SESSION_INACTIVITE_MIN`) ; `current_user` et `get_db` lisent `Authorization: Bearer` avant la session (`core/jeton.py`). Le front ne le garde (sessionStorage) que si `VITE_API_URL` est défini, le renouvelle à mi-durée par `POST /api/auth/renouveler` (compte relu : rôle à jour, supprimé → 401, verrouillé → 403 ; durée totale ≤ `SESSION_MAX_AGE`), l'efface sur 401 et à la déconnexion. En local, le cookie de session reste le seul mode.
  - **Jamais de lien direct vers `/api`** (`href`, `window.open`) : un lien ne transporte pas le jeton. Fichiers par `BoutonFichier` ou `api.ouvrirFichier(url, {telecharger, nom})` (fetch → `Blob` → onglet pour un PDF, téléchargement sinon, nom tiré de `Content-Disposition`). Tests Playwright : ce sont des boutons (`getByRole("button")`), attendre `download.path()` avant la fin du test.

- **Middlewares** (`main.py`) : `SecuriteMiddleware` est ajouté **avant** `SessionMiddleware` (qui l'englobe et lui donne accès à la session). Ne pas inverser l'ordre.

- **`client.js`** : avant d'ajouter des méthodes, vérifier que **toutes** les méthodes `api.*` utilisées dans `src/` existent encore. Commande utile :
  `grep -rhoE "api\.[a-zA-Z]+" frontend/src | sort -u`
- **Listes côté front** : toujours forcer en tableau (`Array.isArray(d) ? d : []`) avant `.map()`.

Tu travailles en autonomie. Tu n'attends pas de validation entre les étapes : tu enchaînes les tâches du **Backlog** ci-dessous, dans l'ordre, jusqu'à ce qu'il soit vide ou qu'une condition d'arrêt soit atteinte.

### Pour chaque tâche
1. **Lire les fichiers réels avant de modifier.** Le dépôt est la source de vérité.
2. Faire des modifications **ciblées** ; ne pas réécrire un fichier entier sans nécessité.
3. Si une base de données est nécessaire : écrire la migration SQL additive (`013_...sql`, `014_...sql`…) et l'exécuter sur la base `labo` avec `psql`.
4. **Vérifier** avant de cocher :
   - syntaxe Python : `python -m py_compile` sur chaque fichier modifié ;
   - front : `npm run build` sans erreur ;
   - API : démarrer uvicorn et appeler les nouvelles routes (curl ou script) quand c'est possible ;

5. Si le dossier est un dépôt git : un commit par tâche, message en français (`feat: ...`, `fix: ...`). Ne jamais faire de `push`.
6. Cocher la tâche dans le Backlog et ajouter une entrée au **Journal** (date, ce qui a été fait, fichiers touchés, actions manuelles éventuelles).
7. Passer à la tâche suivante.

### Quand tu dois choisir
Prends la décision la plus raisonnable, cohérente avec les règles métier et le style existant, et **note-la dans le Journal** (« Décision : … parce que … »). Ne t'arrête pas pour une question de goût ou de détail.

### Conditions d'arrêt (là, tu t'arrêtes et tu demandes)
- Toute opération **destructive** sur les données : `DROP`, `DELETE` de masse, `TRUNCATE`, modification d'une colonne existante, migration non additive.

- Le Backlog est vide : fais alors un résumé final et propose la suite.

À chaque arrêt, écris un message clair en français : ce qui est fait, ce qui bloque, et ce que l'utilisateur doit faire (migration, `pip install`, redémarrage).

**Conclusion** : le modèle de facturation d'Access est clair (**une ligne par analyse, des totaux par section, un bulletin par échantillon, une quittance**), mais il n'a jamais été utilisé. Il n'y a donc **pas de données de paiement à importer**, seulement les prix de `Table Analyses` et `Table Méthode SSA`.

**Décisions par défaut** (validées par l'utilisateur ; elles ne déclenchent pas de condition d'arrêt, mais restent modifiables là où c'est indiqué)

- Monnaie : **dirham marocain**, affiché `1 250,00 DH`. Montants stockés en `numeric(12,2)`, jamais en flottant.
- TVA : **taux configurable, 0 % par défaut** (laboratoire public). Si le taux vaut 0, aucune ligne TVA n'apparaît sur les documents.
- Un **bulletin** (facture) par échantillon par défaut ; on peut aussi regrouper plusieurs échantillons du **même client** dans un seul bulletin.
- Quantité facturée par ligne : **1 par défaut**, modifiable. Une option par analyse (« facturée par prélèvement ») multiplie automatiquement par le nombre de prélèvements de la section.
- Le **prix est figé** sur la ligne au moment où elle est créée : un changement de tarif ne modifie jamais un bulletin existant.
- Un bulletin **émis** n'est plus modifiable. Une correction se fait par un **avoir** (bulletin négatif lié au bulletin d'origine), puis un nouveau bulletin si nécessaire.
- **Exonération** possible (contrôle officiel, convention, autre) avec un motif obligatoire, accordée par un responsable ou un admin.
- Le paiement **ne bloque rien par défaut** : un avertissement s'affiche, et le statut de paiement est visible partout. Un réglage admin permet d'exiger le paiement à une étape (`aucune` / `avant la mise en analyse` / `avant la remise du rapport`) ; valeur par défaut `aucune`.
- Droits :
  - tarifs : admin ;
  - bulletins et encaissements : `user` (accueil) et admin ;
  - exonérations, avoirs et annulations d'encaissement : responsable (s'il existe) et admin ;
  - rôles de section : lecture du statut de paiement seulement.
